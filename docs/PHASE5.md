# 第五阶段 · 优化完善交付说明

第四阶段结束时，功能已经闭环：能看行情、能回测、能受控下单。但整套系统仍是「能跑」的状态，
不是「能用」的状态。这一阶段不新增业务能力，只解决四类会持续消耗使用者耐心的问题：

1. **数据会悄悄错** —— K 线缓存键写错，不同周期/复权共用同一行，图形看着正常但内容是错的。
2. **刷新不可控** —— 行情 10 秒、条件单 15 秒都是写死的常量，移动端既费电又费流量，用户无法干预。
3. **记录看不见** —— 委托与成交只散落在交易页底部，要复盘一笔单子得自己记时间点。
4. **首屏太重** —— 所有页面静态导入，构建出单个 2.5 MB chunk（gzip 808 KB），冷启动要等整包下载。

本阶段的原则是：**先修「结果错误」，再修「体验不适」，最后修「加载太慢」**。
顺序不能反 —— 性能优化会把问题藏得更深，一个错误的缓存键在分包之后只会更难定位。

## 一、缺陷修复：K 线缓存键

### 1.1 问题是什么

缓存表 `kline_cache` 的主键是 `(symbol, period, adjust)`，建表时是对的。
但写入路径把整串键拼成了一个字符串，塞进 `symbol` 列：

```ts
// 修复前（错误）
const key = `${symbol}:${period}:${adjust}`
await db.execute(
  'INSERT INTO kline_cache (symbol, period, adjust, ...) VALUES (?, ?, ?, ...)',
  [key, 'cache', 'cache', ...],
)
```

后果是：`600519:day:qfq` 和 `600519:day:none` 读出的是同一行数据。
**这不是显示问题，是数据正确性问题** —— 用户选了前复权，看到的可能是不复权价格，
回测里所有涉及除权的标的收益率都会算错，而且完全没有报错。

### 1.2 为什么之前没被发现

三个因素叠加：

| 因素 | 说明 |
|------|------|
| 大多数标的短期无除权 | 不复权与前复权在无分红送转期间数值相同，肉眼无法分辨 |
| 默认参数一致 | 默认就是 `day` + 前复权，只要不改参数，缓存键的坍缩不会暴露 |
| 无一致性校验 | 没有「同一标的不同周期条数不应相同」这类断言 |

### 1.3 怎么修的

拆开解析、分列写入，读时先查规范键、未命中再回退旧行：

```ts
function splitKey(key: string): { symbol: string; period: string; adjust: string } | null
```

关键取舍：**兼容旧数据而不是直接清库**。已写入的旧行 `period`/`adjust` 都是字面量 `'cache'`，
但它们承载的是真实的历史行情，删掉意味着用户下次打开任何标的都要重新走一遍网络请求。
所以 `readCache` 的顺序是：

1. 按规范三维键查 —— 命中即返回（新数据走这条）
2. 未命中，再按「整串键 + `cache`/`cache`」查旧格式 —— 命中则**顺手迁移**成规范行
3. 都未命中才算 miss

迁移是「读时惰性迁移」，不是启动时批量刷库。原因：启动批量迁移会在冷启动时锁住数据库，
而真正的迁移只需要在每个标的第一次被打开时完成，摊薄到用户无感知。

### 1.4 顺带补的维护能力

原来缓存表只增不减，用久了会无限膨胀。补了三个函数：

- `pruneCache(keepDays)` —— 删除超过保留天数的行，按 `updated_at` 判断
- `cacheStats()` —— 返回总条数、最早/最新时间，供设置页展示
- `clearAllCache()` —— 全量清空，给「缓存明显异常」时一个干净的重置手段

## 二、轮询重构：让刷新间隔可配且不折腾设备

### 2.1 原来的实现与问题

`MarketPage` 与 `TradePage` 各自 `setInterval`，间隔写死（行情 10s / 非交易 60s，条件单 15s）。三个问题：

| 问题 | 实际后果 |
|------|----------|
| 无失败退避 | 网关挂掉或断网时，每 15 秒打一次错误日志，日志被刷满，真正的错误被埋掉 |
| 无可见性判断 | 窗口最小化 / App 切后台后仍在轮询，移动端持续耗电耗流量 |
| 间隔不可配 | 用 WiFi 的用户想更快、用流量的用户想更慢，都没有出口 |

### 2.2 重写后的 `usePolling`

保留单一职责（只管「按节奏调用一个异步函数」），把三个能力内聚进去：

**失败退避**：连续失败时间隔翻倍，封顶 `maxIntervalMs`；一旦成功立刻复位到基准值。
封顶很重要 —— 无上限退避会让「网络恢复后很久才刷新一次」，用户以为数据是新的。

**可见性暂停**：`document.hidden` 为真时跳过本轮。注意是**跳过执行**而不是清除定时器，
清定时器再重建容易在频繁切换前后台时产生多个定时器实例。

**回前台补刷**：`visibilitychange` 变可见时，若距上次成功刷新已超过基准间隔，立即触发一次。
只靠「恢复轮询」不够 —— 用户切回来看到的第一眼必须是新数据。

**闭包陷阱**：用 ref 持有最新的 `fetcher` 与 `failures`，避免把 `fetcher` 放进 `useEffect` 依赖
导致每次渲染都重建定时器（这也是原实现里 interval 抖动的原因之一）。

### 2.3 设置项

`settings.ts` 增加三项并做 v1→v2 迁移（老配置补齐默认值，不清空用户已有设置）：

| 字段 | 默认 | 可选 | 说明 |
|------|------|------|------|
| `quoteRefreshMs` | 10000 | 0 / 5s / 10s / 30s / 60s | 0 = 关闭自动刷新 |
| `tradePollMs` | 15000 | 0 / 5s / 10s / 15s / 30s / 60s | 条件单评估节奏 |
| `cacheKeepDays` | 7 | 0–365 | K 线缓存保留天数 |

`0` 的语义是「关闭」，不是「尽可能快」。这点在 UI 上明确标注，否则 0 很容易被理解成「实时」。

### 2.4 非交易时段的处理

`MarketPage` 用 `effectiveInterval()` 计算实际间隔：交易时段用配置值，非交易时段放宽到 60 秒，
但**不超过**用户配置值。这样既避免收盘后每 5 秒空转，也尊重「我就想 5 秒一次」的显式选择。

`TradePage` 的条件单轮询设为 0 时，只做一次评估后关闭定时器 —— 条件单本身需要持续判定，
所以这里同时给了个提醒：关闭后不会自动触发。不静默降级，是这一阶段的另一条底线。

## 三、交易日志：从「看不见」到「可复盘」

### 3.1 为什么单独开一页

原来日志内嵌在交易页底部，只能看最近若干条，没有筛选、没有汇总、不能导出。
复盘一笔单子需要「这笔为什么没成交」「当天一共买了多少」时，基本靠手算。

独立成页的理由不是「界面上放不下」，是**用途不同**：交易页是「现在要下单」，
日志页是「事后要查账」。两件事的操作路径、停留时长、信息密度都不一样，混在一起两边都做不好。

### 3.2 能力

**筛选**：日期区间（含今日/近 7 天/近 30 天/全部快捷选项）+ 关键词（代码或名称模糊匹配）
+ 方向 + 状态 + 来源（手动/条件单/策略）。五个维度可叠加。

**汇总**：买入金额、卖出金额、有效成交额、拦截笔数、失败笔数。
把「拦截」和「失败」单列，是因为它们的信息价值完全不同 —— 拦截说明风控在起作用（正常），
失败说明链路有问题（要查）。

**导出**：CSV 带 BOM 头。这一条不是细节洁癖 —— 不带 BOM 的 UTF-8 CSV 在 Excel 里打开，
标的名称为中文时全是乱码，导出功能等于废掉。

**清理**：删除 90 天前记录，带二次确认。交易记录属于审计材料，默认不自动删，
只提供手动入口，避免「回头查一笔半年前的账发现没了」。

### 3.3 实现要点

`ledgerReport.ts` 独立于页面，负责 SQL 与格式化：

- `queryOrders()` —— 动态拼 WHERE，参数化绑定，不做字符串拼接（防注入，且能命中索引）
- `summarize()` —— 汇总在 SQL 里做，不把全量行拉到前端再累加
- `ordersToCsv()` / `downloadCsv()` —— 转义遵循 RFC 4180（字段含逗号/引号/换行时加引号并双写引号）
- `purgeOrdersBefore()` —— 按时间阈值删除

## 四、索引迁移 0006

新增 5 个索引，全部来自本阶段新增查询的实际 WHERE/ORDER BY 列：

| 索引 | 支撑的查询 |
|------|-----------|
| `idx_orders_status_created` | 日志页按状态筛选 + 时间排序 |
| `idx_orders_side_created` | 按方向筛选 + 时间排序 |
| `idx_orders_source` | 按来源筛选 |
| `idx_conditional_state_date` | 条件单按状态 + 日期扫描（轮询热路径） |
| `idx_fills_time` | 成交按时间区间查询 |

只加「真的被查询用到」的索引。索引不是免费的：每个索引都要在写入时维护，
交易记录是写多读少的表，无差别加索引会拖慢下单路径。

## 五、首屏性能：为什么必须拆包

### 5.1 拆之前的状态

所有页面静态导入，构建产物是单个 2.5 MB chunk（gzip 808 KB）。三个后果都很具体：

1. 移动端冷启动要等整包下载完才能看到界面，弱网下非常明显；
2. 只打开行情页的用户也要下载回测、交易、资金等页面的代码；
3. WebView 解析 2.5 MB JS 的耗时会计入首屏，低端安卓机上有感。

### 5.2 两层手段

**路由懒加载**：9 个页面全部 `React.lazy`，首屏只加载「布局 + 首页」。
每个页面保持独立 `import` 声明，而不是集中在一处 map 里 —— 这样 Vite 能静态分析依赖边界，
分包才不会互相牵连。

占位用固定高度的居中 Spin，而不是骨架屏：懒加载通常只有几十到几百毫秒，
骨架屏反而造成「闪一下骨架再闪一下内容」的观感。

**manualChunks 分层**：按「升级频率」而不是「功能归属」切分。

| chunk | 内容 | 理由 |
|-------|------|------|
| `charts` | echarts + zrender | 最重（约 1 MB），只有详情页/回测页需要，首页完全不加载 |
| `ui` | antd + rc-* + @ant-design | 版本升级时才变，日常开发改动不污染其缓存 |
| `react` | react 全家桶 + 路由运行时 | 几乎不变，缓存命中率最高 |
| `vendor` | 其余三方依赖 | 变更频率居中 |

### 5.3 一个真实踩到的坑：循环 chunk

第一版按「echarts / antd / react / vendor」四分，构建报出两个警告：

```
Circular chunk: vendor -> react -> vendor
Circular chunk: vendor -> antd  -> vendor
```

原因是分包边界切在了有依赖回边的位置：

- `react-router` 归入 react 块，但它依赖的 `@remix-run/router` 落在 vendor，于是 react → vendor → react；
- `antd` 单独成块，但 `rc-*` 组件族散落在 vendor，两边互相引用。

循环 chunk 不是警告级别的瑕疵 —— 它意味着运行时初始化顺序不确定，
极端情况会出现「某模块读到未初始化的导出」的白屏，而且只在特定页面复现，极难排查。

修正思路是**让依赖图在块级别成为有向无环**：

- 把 `zrender` 与 echarts 放在同一块（它本来就是 echarts 的渲染内核）；
- 把路由的运行时依赖（`@remix-run`、`cookie`、`set-cookie-parser`）一并归入 react；
- 把 `rc-*`、`@rc-component`、`@ant-design` 全部归入 ui，使边只剩 `ui → vendor` 单向。

修正后构建无警告。

### 5.4 效果

| 指标 | 拆前 | 拆后 |
|------|------|------|
| 首屏必须加载 | 2.5 MB（单块） | index + react + ui + vendor，charts 不加载 |
| 页面级 chunk | 无 | 4–33 KB / 页 |
| charts（按需） | 混在主包 | 独立 1.05 MB，仅详情页/回测页加载 |

进一步可做的（本阶段未做，留作后续）：ui 块仍有 1.05 MB，主要来自 antd 全量引入。
改为按需引入或换成更轻的组件库能再降一截，但会动到全部页面的写法，
与「本阶段只做优化、不改业务代码」的约束冲突，因此单列。
